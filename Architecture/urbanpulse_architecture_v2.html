Architecture Decision: Why Lambda + Kappa Hybrid?
MetroConnect's dual SLA requirement makes this genuinely contested — unlike most commercial streaming scenarios
κ Kappa Layer ✓ CHOSEN for RT
⚡ Sub-2-min AQI alert SLA — tumbling 1-min Flink windows; pure streaming delivers <15 sec end-to-end
🚦 90-sec signal adaptation — stateful stream joins on traffic + GPS; batch cannot satisfy this
🗂️ Single code path — Flink handles both alerting AND replayable historical queries via Kafka offset replay, reducing maintenance burden
💾 Kafka as durable log — 7-day retention means stream can be replayed if hot-path fails, eliminating the need for a separate batch ingest pipeline
Λ Lambda Layer ✓ CHOSEN for Batch
📊 Weekly councillor reports — complex multi-ward aggregations, hotspot maps, PDF generation; Spark excels here, not Flink
🏛️ Monthly state government submission — regulatory-format output with 7-year audit trail; needs immutable Parquet-on-S3 cold store, not stream state
🤖 ML demand forecasting — 30-day smart-meter history for next-week ward demand curves; batch ML pipelines on Spark are mature and cost-effective
🔄 Late-arriving data correction — sensor outages create gaps; batch reprocessing over cold store corrects historical inaccuracies impossible in pure Kappa
Verdict: Pure Kappa fails for regulatory-grade batch reporting (councillors, state submissions, ML re-training). Pure Lambda adds unacceptable latency for the 90-second signal control and sub-2-minute AQI alert SLAs. The Lambda + Kappa Hybrid uses a single Kafka event bus consumed independently by: (A) an Apache Flink speed/Kappa layer for real-time SLAs, and (B) an Apache Spark batch/Lambda layer for analytical and compliance workloads — each writing to purpose-fit storage.

④ Storage Layer Polyglot persistence — right database for each workload Four purpose-fit stores · zero one-size-fits-all
Time-Series DB
InfluxDB 3.0
🌫️⚡ Sensor time-series data
Stores all AQ sensor readings (PM2.5, PM10, NO₂, AQI) and smart-meter telemetry (kWh, voltage, power factor). Native columnar time-series compression with InfluxQL / Flux queries optimised for windowed aggregations.
Why InfluxDB? Purpose-built for high-frequency append-only sensor writes (~1,160 ev/s). Native downsampling tasks (5 min → 1 hr → 1 day) reduce storage cost 10×. InfluxQL window functions drive the Grafana dashboard sparklines with sub-second query latency.
Write throughput~1,160 ev/s
Hot retention30 days
Downsampling5m → 1h → 1d
WriterFlink Sink
ReadersGrafana, Advisory API
Geospatial DB
PostGIS (PostgreSQL)
🚌 Bus GPS positions
Stores current and recent bus positions as PostGIS geometry points with GIST spatial index. Enables radius queries, route-polygon intersection tests, and geofencing alerts for proximity-aware transit information.
Why PostGIS? Only database with mature ST_DWithin, ST_Intersects, and route-polygon joins that the Transit Passenger App API needs. GIST index makes "buses within 500 m of stop" queries execute in <10 ms even at 2,400 GPS ev/s write load.
Write throughput~2,400 ev/s
Hot windowLast 2 hours
IndexGIST on geom
WriterFlink Sink → JDBC
ReadersTransit dashboard, Public API
Columnar Data Lake
Apache Parquet on S3
📜 Historical AQI records
Long-term cold storage of all AQI and sensor observations, partitioned by year/month/zone in Parquet format. Queried by Spark batch jobs for multi-year trend analysis and monthly state government regulatory submissions.
Why Parquet/S3? 7-year statutory retention at near-zero storage cost. Columnar Parquet gives 10–20× compression vs JSON. Spark reads directly without schema migration. AWS Glue/Hive metastore enables ad-hoc Athena SQL for ad-hoc councillor queries.
Retention7 years (statutory)
Partition schemeyear / month / zone
CatalogAWS Glue / Hive
WriterKafka Connect S3 Sink
ReadersSpark, Athena
OLAP / Data Warehouse
Apache Druid
🏛️ Councillor report aggregates
Pre-aggregated OLAP cubes for weekly and monthly councillor dashboards. Sub-second drill-down on ward × pollutant × week dimensions. Also stores transit KPI aggregates and ML demand forecast outputs loaded by Spark.
Why Apache Druid? Sub-500 ms query latency on multi-dimensional aggregations that councillors need (ward + zone + metric + date range). Druid's real-time ingestion can optionally ingest Kafka for near-real-time OLAP alongside batch Spark loads.
